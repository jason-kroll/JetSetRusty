# PLAN: replace the C-era fn-pointer dispatcher with a typed screen state machine

Task: eliminate every global fn-pointer slot — the four main dispatcher
slots (`ACTION`/`RESPONDER`/`TICKER`/`DRAWER` as `thread_local! Cell<Event>`
with `Event = Option<fn()>` in `common.rs`) plus the same C-ism in miniature:
`rope.rs`'s `ROPE_TICKER`/`ROPE_DRAWER`, `game.rs`'s `DO_CLOCK_UPDATE`,
`cheat.rs`'s `cheat_responder() -> Event`, `robots.rs`'s
`Robot.do_move: MoveFn` / `do_draw: DrawFn` vtables, and `audio.rs`'s
`Channel.do_phase: Event` / `SfxInfo.do_sfx`/`do_play`. The end state is an
`enum Screen` (with per-screen phase enums) matched in the dispatcher.

**Behaviour-preserving refactor only**: every existing golden must pass
*unchanged* after every phase — never run `UPDATE_GOLDEN=1` under this
plan. If any test fails at any point, stop, revert that commit, and report.

## Status: PENDING REVIEW

## Why

State transitions currently work by mutating `Option<fn()>` globals at
runtime (`set_action(Some(title_action))`, one-shot `set_action(Some(
do_nothing))`, `robot.do_move = do_move_right`). That is C's
`EVENT = void(*)(void)` pattern, not idiomatic Rust: the compiler cannot
see which handler runs, `None` means both "off" and "no-op", and nothing
prevents an inconsistent combination of the four slots. Rust's shape for
this is a single `enum` state value matched in one place.

## Hard invariant: the frame-boundary timing must not move

`game_frame` (game_main.rs:365) reads the slots at four fixed points, and
**when** a mutation becomes visible is load-bearing:

1. step 1: read+fire ACTION. Mutations to ACTION (from anywhere) take
   effect at step 1 of the *next* frame — this is the deferred transition
   (`set_action(Some(title_action))` from a ticker runs next frame, while
   this frame's drawer still runs).
2. step 2: per queued input, read+fire RESPONDER. Responder mutations to
   TICKER/DRAWER apply at steps 4/5 of the *same* frame (e.g.
   `game_pause(true)` from `do_game_responder`); responder mutations apply
   to later inputs in the same loop.
3. step 4: read+fire TICKER. Ticker mutations to DRAWER apply same frame,
   to TICKER next frame.
4. step 5: read+fire DRAWER. Drawer mutations apply next frame
   (loader's drawer1→drawer2→drawer3 chain, `do_draw_once`).

The refactor keeps these four read points and their order exactly; only
the *type* stored at each point changes (`Option<fn()>` → enum). The
golden replays (which cover every screen and every transition: `idle`
loader+codes, `title`, `play` start/pause/mute/escape, `victory`
toilet→title, `death`, `gameover`, `cheat` incl. `ReinitRoom`,
`sweep-00..59` incl. the replay `set level` direct ticker write) are the
proof. A unit test in the new dispatch module should pin the deferral
rules (queued action fires next step 1; phase writes from a responder are
visible at the same frame's step 4).

Subtle point: `game_init_room` is invoked through *two* different slots —
queued as ACTION by `cheat.rs` (runs step 1) and set as TICKER by
`game_action` and `replay.rs` (runs step 4) — and its slot writes land
differently in each case. The new design must keep both entry paths:
`Pending::ReinitRoom` (consumed at step 1) vs. directly setting the game
phase to `Init` (read at step 4 of the current frame, which is what
`replay.rs`'s `set level` needs — it pokes before `game_frame` runs).

## Target design

New module `src/dispatch.rs`. All state is one `Copy` struct in a single
`thread_local! Cell` (no `RefCell` needed — reads copy out, writes copy
in, mirroring today's `Cell::get`/`Cell::set`; this also respects
CONVENTIONS.md's "prefer restructuring over `Rc<RefCell<_>>`"):

```rust
enum Screen {
    Loader(LoaderPhase),   // Enter | Bar | Ready   (drawer1 → drawer2 → drawer3+ticker)
    Codes,
    Title(TitlePhase),     // Init | Scroll          (do_title_init → do_title_ticker loop)
    Game(GamePhase),       // Init | Play | Pause | PauseCheat | PausedDrawOnce
    Die(DiePhase),         // Init | Anim
    GameOver(GameOverPhase), // Init | Run
}

enum Pending {             // the old ACTION slot, consumed at step 1
    None,
    Enter(Screen),         // run the screen's enter work, install fresh phase
    StartGame,             // title's game_start: reset + Enter(Game)
    ReinitRoom,            // game_init_room one-shot (cheat level select)
}

struct Dispatch { screen: Screen, pending: Pending }  // Copy
```

`dispatch.rs` exposes `dispatch() -> Dispatch`, `update(|&mut Dispatch|)`,
`queue_pending(Pending)`, `set_screen(Screen)`, and derives the three
handlers by matching `screen` — the single place a `Screen` is matched:

```rust
fn responder(d: &Dispatch) -> ... { match d.screen { ... } }
fn ticker(d: &Dispatch)    -> ... { match d.screen { ... } }
fn drawer(d: &Dispatch)    -> ... { match d.screen { ... } }
```

`game_frame` becomes: take `pending` out of the cell (set `None`), run it
at step 1; per input, copy out the responder kind and match-call; copy out
ticker kind at step 4; drawer kind at step 5. The per-screen handler fns
(`do_loader_ticker`, `do_game_ticker`, `die_ticker`, …) stay in their
modules, now called from the match arms instead of through pointers.
Screen *enter* work (e.g. `codes_action`'s drawing + `get_code`) becomes
the body of consuming `Pending::Enter(screen)`; slot installs inside
handlers become phase assignments (`screen = Screen::Loader(LoaderPhase::Bar)`).

Thread-locality stays: the SDL audio callback never touches the dispatch
state, so main-thread-only `Cell` is sound, same argument as today.
`GAME_INPUT`/`VIDEO_FLASH` are plain data, not fn pointers — out of
scope. `do_quit` stays a plain fn (it sets `GAME_RUNNING`); `do_nothing`
and `fire()` disappear.

## Phases (one commit each, all gates green after each)

1. **Typed slots, mechanical swap.** Replace the four `Cell<Event>` with
   four `Cell<TypedEnum>` (`Action`, `Responder`, `Ticker`, `Drawer` enums
   whose variants enumerate today's fn values 1:1) — same read points in
   `game_frame`, call sites renamed mechanically
   (`set_action(Some(title_action))` → `set_action(Action::Title)`).
   Goldens byte-identical. This alone removes the fn pointers from the
   main dispatcher with zero behavioural surface.
2. **Collapse to `Screen` + phases.** Merge the four slots into
   `Cell<Dispatch>` as above; handlers derived by matching `screen`.
   Initial state mirrors `ACTION = loader_action`. Add the deferral unit
   test. Goldens byte-identical.
3. **Sub-slots.** `rope.rs`: `ROPE_TICKER`/`ROPE_DRAWER` are only ever
   both-set-or-both-`do_nothing` → one `Cell<bool>` "rope active"; `game.rs`
   calls `rope::rope_tick()/rope_draw()` which internally no-op when
   inactive. `game.rs` `DO_CLOCK_UPDATE` is None-vs-`do_draw_clock` →
   `Cell<bool>` `clock_redraw`. `cheat.rs`: `cheat_responder() -> Event`
   → returns a `CheatHandler` enum matched at the call site in
   `do_game_responder`.
4. **Robots vtables.** `do_move: MoveFn` → `enum Move { Nothing, Left,
   Right, Up, Down, Static, ArrowLeft, ArrowRight }`; `do_draw: DrawFn` →
   `enum Draw { Nothing, Robot, Toilet, Arrow }`. Bounce becomes
   `robot.move = Move::Right`; `robots_ticker`/`robots_drawer` match on the
   enum (or call `robot.step()` / `robot.draw()` with the match inside
   `robots.rs`). All in `robots.rs`, no external call sites.
5. **Audio.** `Channel.do_phase: Event` is a pure on/off flag
   (`Some(do_phase_fn)` where the body is empty) → `on: bool`.
   `SfxInfo.do_sfx`/`do_play` are trampolines that take `&mut AudioState`
   because `audio_output` already holds the `AUDIO_STATE` lock →
   `enum SfxHandler { Off, On, Play, Willy }` matched at the two call
   sites, calling the underlying fns directly. Then delete
   `pub type Event` from `common.rs` — no `Event` left anywhere.
6. **Docs.** Update AGENTS.md's Architecture section (it currently
   documents the four fn-pointer slots and `Event = Option<fn()>` —
   those paragraphs describe the design this plan removes) and sweep
   comments that cite "Event function-pointer globals" (`game.rs:234`,
   `game.rs:680`, `rope.rs:154`, …).

## AGENTS.md disagreements (to apply in phase 6)

AGENTS.md's architecture section says the main loop "drives the loop via
four global function pointers" living in `thread_local! Cell`s and that
"`Event` is `Option<fn()>`, so an unset slot is `None`". That is a
description of the C-ism being removed, not a rule — after this plan it
will read "a single `Copy` `Dispatch { screen, pending }` state matched
in the dispatcher". No commit-related instructions are affected.

## Risks

- **Timing drift** (deferred vs. same-frame visibility) — mitigated by
  keeping the four read points and by the golden suite, which exercises
  every transition; the unit test pins the rules.
- **Loader's conditional installs** — `do_loader_drawer2` installs
  responder/ticker/drawer only when the music has stopped; in the enum
  world that is a phase transition `Bar → Ready`, read next frame exactly
  as today.
- **Replay `set level`** must write the phase *directly* (step 4 same
  frame), not via `Pending` — called out above.
- **Audio trampolines** exist for mutex reentrancy; the enum match keeps
  the `&mut AudioState` argument passing unchanged.
